# 1. Purpose

Phase 1 is **NOT about building business screens yet**.

The goal is to establish the **frontend architecture and application shell** so future feature implementation becomes straightforward.

At the end of Phase 1, the CRM frontend should have:

- Complete folder architecture
- Protected routing
- Auth foundation
- API client
- Global providers
- App shell
- Sidebar navigation
- Topbar
- Command palette foundation
- Placeholder pages for all major routes
- Permission-aware navigation
- Ready to build actual modules (dashboard, leads, etc.)

No final business UI is required in this phase.

# 3. Architectural Decisions

## 3.1 Feature-based structure

We will use **feature-first organization**, not generic component dumping.

Good:

```bash
features/
  auth/
  leads/
  users/
  dashboard/
```

Avoid:

```bash
components/
  everything...
```

Reason:

CRMPro is large and modular:

- leads
- pipelines
- users
- roles
- analytics
- notifications
- audit

Feature isolation improves maintainability.

---

## 3.2 Route protection

Chosen strategy:

## Client-side protected shell

We will NOT rely on Next middleware for auth.

Reason:

Backend auth is:

- JWT access token
- refresh token
- session rotation

Middleware adds unnecessary complexity.

Protected routes will be wrapped by:

```tsx
<ProtectedLayout>
  <AppShell />
</ProtectedLayout>
```

Behavior:

- Load current user session
- Validate access token
- Auto-refresh if expired
- Redirect to `/login` if unauthenticated

---

## 3.3 API communication

Use a reusable typed API client.

Structure:

```bash
src/lib/api/
  client.ts
  auth.ts
  leads.ts
  users.ts
  roles.ts
```

Responsibilities:

- Attach access token
- Refresh on 401
- Parse standardized backend errors
- Normalize API responses
- Centralize retry logic

Backend success shape:

```json
{
  "success": true,
  "data": {}
}
```

Backend error shape:

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "Readable message",
    "details": null
  }
}
```

Frontend must consume this globally.

# 4. Auth Strategy

Chosen strategy:

## Access token in memory + refresh token in httpOnly cookie

Why:

- Better security than localStorage
- Keeps XSS blast radius lower
- Still easy to work with in SPA mode

---

## Required backend changes (CRM API)

Auth endpoints must be updated.

### Login

Current:
Returns access + refresh tokens in body.

Target:

Response body:

```json
{
  "success": true,
  "data": {
    "accessToken": "...",
    "user": {}
  }
}
```

Response cookie:

```http
Set-Cookie: refresh_token=...; HttpOnly; Secure; SameSite=Lax
```

---

### Refresh

Current:
Client sends refresh token.

Target:
Backend reads cookie automatically.

Returns:

```json
{
  "success": true,
  "data": {
    "accessToken": "..."
  }
}
```

Also rotates refresh cookie.

---

### Logout

Must:

- revoke session
- clear refresh cookie

# 9. Route Configuration

Routes must be config-driven.

Do NOT hardcode sidebar JSX.

Create:

```bash
src/config/routes.ts
```

Each route contains:

```ts
{
  label: "Users",
  href: "/users",
  icon: AppIcons.users,
  requiredPermissions: ["user.read"],
  searchable: true,
  keywords: ["team", "staff"]
}
```

Used by:

- sidebar
- route guards
- command palette
- breadcrumbs
